# Test-Case Web

## 使用场景

当用户要求你根据书面的测试用例文档测试网站并保留证据时，使用此技能。

此工作流专为需要认证、有状态的浏览器测试设计。除非用户明确要求使用其他浏览器，否则始终优先使用 `@chrome` 和 Chrome 技能。许多真实的 QA 流程依赖于用户现有的会话、SSO、企业登录或多标签页行为。

此工作流不要默认使用应用内浏览器。如果 Chrome 可用，请使用 Chrome。

## 不要使用

以下情况不要使用此技能：
- 针对具体变更的代码审查（请使用 code-reviewer）
- 详细检查单个提交
- 除日志提取外的 Git 操作（分支、合并等）
- 与 Git 无关的报告生成

## 使用说明

按顺序执行以下步骤。

### 1. 读取测试用例来源

从用户提供的文档开始。如果用户指定了子章节（如 `1.5`）或标题（如 `@ 按钮功能`），首先将范围限定到该章节。

为每个测试用例提取：

- 用例编号
- 标题
- 前置条件
- 操作步骤
- 预期结果

如果文档编码混乱，从附近的标题和表格结构中尽可能恢复信息，而不是立即停止。

如果用户没有指定章节且文档很大，识别主要章节并只测试请求的区域。如果请求不明确，提出一个简洁的澄清问题。

### 2. 在 Chrome/Edge 中打开目标网站

使用 `@chrome` / Chrome / Edge支持的浏览器自动化，除非用户明确要求，否则不要使用应用内浏览器。

将此作为硬性默认规则：

- 始终在用户的真实 Chrome / Edge 环境中打开目标网站
- 保持工作标签页可供用户查看和交互
- 当用户需要操作时，不要将关键的登录页面隐藏在仅后台的流程中

打开请求的网站并检查流程是否已认证。

如果需要登录：

- 清楚告知用户需要登录
- 告知用户已为其在 Chrome 中打开页面
- 保持浏览器停留在正确的页面
- 将标签页保持为可见的交接物，供用户使用
- 等待用户完成登录
- 用户确认已登录后，从同一个 Chrome / Edge 会话继续

不要尝试绕过登录。不要要求用户重复你通过现有 Chrome / Edge 标签页可以保留的工作。

当需要登录或手动操作时，将 Chrome / Edge 标签页视为交接物，而不是隐藏的实现细节。

### 3. 逐个执行测试用例

对每个测试用例：

1. 从文档中向自己重述测试意图。
2. 将页面带入所需状态。
3. 只执行最少必要的操作。
4. 将实际行为与预期结果对比。
5. 在继续之前捕获证据。

对每个执行的测试用例，至少捕获：

- 一张支持最终结论的截图

在以下情况捕获额外截图：

- 用例失败时
- 状态跨步骤变化时
- 有前后对比证据更容易理解缺陷时

使用保留执行顺序和用例可追溯性的截图文件名：

- `TC-V-1.5-01-01.png`
- `TC-V-1.5-01-02.png`

如果用例因阻塞无法完成，仍然捕获截图并将用例标记为 `blocked`。

### 4. 在过程中记录结构化结果

在运行期间逐步创建 `results.json`。使用以下结构：

```json
{
  "run_name": "at-button",
  "target_url": "https://example.com",
  "source_document": "/absolute/path/to/cases.md",
  "section": "1.5 @ 按钮功能",
  "generated_at": "2026-05-11T14:30:00+08:00",
  "cases": [
    {
      "id": "TC-V-1.5-01",
      "title": "全能参考模式显示 @ 按钮",
      "preconditions": "选中全能参考模式",
      "steps": "查看网络搜索按钮右侧",
      "expected": "显示 @ 按钮",
      "actual": "在全能参考模式下，网络搜索按钮右侧显示引用参考按钮。",
      "status": "passed",
      "notes": "",
      "screenshots": [
        "screenshots/TC-V-1.5-01-01.png"
      ]
    }
  ],
  "summary": {
    "passed": 1,
    "failed": 0,
    "blocked": 0,
    "not_run": 0
  }
}
```

允许的用例状态值：

- `passed`（通过）
- `failed`（失败）
- `blocked`（阻塞）
- `not_run`（未执行）

仅在用户显式缩小范围或停止运行时使用 `not_run`。

### 5. 编写 `测试结果.md`

执行完成后，编写简洁但完整的 Markdown 报告。

使用以下结构：

```md
# 测试结果

## 测试范围
- 目标网站：
- 测试文档：
- 测试章节：
- 测试时间：

## 汇总
- Passed：
- Failed：
- Blocked：
- Not Run：

## 逐条结果

### TC-XXX
- 标题：
- 预期：
- 实际：
- 结果：Passed / Failed / Blocked / Not Run
- 证据：
  - [截图1](./screenshots/TC-XXX-01.png)
```

要求：

- 每个执行的用例都必须出现
- 每个用例必须链接到其截图
- 失败的用例应清楚解释差异
- 阻塞的用例应清楚解释阻塞原因

### 6. 生成 `测试结果.html`

`results.json` 完成后，使用捆绑的脚本：

`scripts/generate_html_report.py`

该脚本将 `results.json` 转换为 `测试结果.html`，包含：

- 汇总卡片
- 逐条结果表格
- 逐条截图画廊
- 颜色编码的状态徽章

除非脚本缺失或损坏，否则不要手写 HTML。如果脚本失败，修复输入或脚本后重新运行。

## 实用测试指南

### 登录处理

当登录中断运行时：

- 保留当前 Chrome / Edge 标签页
- 将相关 Chrome / Edge 标签页留给用户，而不是关闭或省略
- 准确告知用户你的需求，例如："请先在 Chrome / Edge 中完成登录，登录完成后我继续测试。"
- 明确说明页面已在 Chrome / Edge 中打开并等待他们
- 用户确认后，重新发现或回收活动站点标签页并继续

如果用户说看不到页面，重新打开或回收正确的 Chrome / Edge标签页，并在要求他们继续之前将其保持为活动交接标签页。

### 证据质量

优先选择能让结论一目了然的截图：

- 相关控件可见
- 活动模式或选中的筛选器可见
- 预期或意外状态可见

避免需要读者猜测正在测试什么的截图。

### 范围控制

如果文档包含多个章节，不要静默测试所有内容。首先尊重用户请求的章节。

### 报告诚实性

除非观察到的行为与预期结果一致，否则不要将测试标记为通过。

如果浏览器自动化路径变得不稳定，记录阻塞并附带证据，而不是编造确定性结论。

## 建议的触发示例

以下请求应触发此技能：

- "根据这个测试用例文档测试这个网站"
- "按这个 markdown 测试 1.5 @ 按钮功能"
- "帮我 QA 这个页面，结果要带截图"
- "登录后继续跑这些网页用例，并生成测试报告"
- "根据测试文档验证这个 web app，并导出 html 报告"
- "@chrome 打开这个网站并按测试文档执行"
